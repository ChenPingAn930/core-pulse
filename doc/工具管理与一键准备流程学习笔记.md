# CorePulse 工具管理与一键准备流程学习笔记

> 本文记录 CorePulse 对本地第三方维修工具所做的完善工作，帮助理解“工具为什么需要统一管理、如何判断工具可用、如何安全下载和准备工具”。

## 一、为什么要做工具管理

CorePulse 不是只返回文字建议的聊天程序，它还需要真正调用 Windows 上的外部工具，例如 FurMark、CPU-Z、GPU-Z、smartctl 和 CrystalDiskMark。

如果直接启动这些工具，容易出现以下问题：

- 工具文件不存在，导致进程启动失败；
- 工具入口文件存在，但配套 DLL、资源目录或子程序缺失；
- 下载链接返回的是网页，而不是 exe 或 zip 文件；
- 下载文件被损坏，或者内容被替换；
- zip 解压时覆盖了错误目录；
- 安装器需要管理员权限，但程序没有明确提示用户；
- 一键准备遇到一个失败工具后，其他工具也没有继续检查。

因此，工具管理的核心目标是：

```text
定义工具
  -> 检查状态
  -> 必要时下载或启动安装器
  -> 校验文件
  -> 解压并发布
  -> 检查入口文件和依赖
  -> 返回每个工具的最终状态
```

这样，后续真正执行检测或压力测试时，可以先确认工具是否处于 `READY` 状态。

## 二、主要修改位置

### 1. `ToolManagerService`

文件：

```text
corepulse-system/src/main/java/com/corepulse/system/service/ToolManagerService.java
```

这是工具管理的核心服务，主要负责：

- 保存工具定义；
- 检查工具状态；
- 下载文件；
- 校验文件类型和 SHA-256；
- 安全解压 zip；
- 检查依赖文件；
- 启动需要管理员权限的安装器；
- 汇总一键准备结果。

### 2. `ToolManagerController`

文件：

```text
corepulse-system/src/main/java/com/corepulse/system/controller/ToolManagerController.java
```

它把工具管理能力暴露为 HTTP 接口：

| 接口 | 作用 |
|---|---|
| `GET /api/tools/manager/status` | 查询所有工具当前状态 |
| `POST /api/tools/manager/prepare` | 下载、安装或检查工具 |
| `POST /api/tools/manager/install` | 安装 VC++ 运行库 |

Controller 的职责比较简单：接收请求参数，再调用 Service。真正的业务逻辑放在 Service 中，便于维护和测试。

### 3. `ToolPathConfig`

文件：

```text
corepulse-system/src/main/java/com/corepulse/system/tool/ToolPathConfig.java
```

它集中保存所有工具路径，例如：

```text
./tool/烤鸡工具/FurMark/FurMark.exe
./tool/处理器工具/CPUZ/cpuz_x64.exe
./tool/硬盘工具/smartmontools/bin/smartctl.exe
```

集中管理路径的好处是：

- 不需要在多个工具类中重复写路径；
- 路径发生变化时只需要修改一个配置类或 `application.yml`；
- 工具管理器和真正执行工具使用同一份路径配置，避免“检查的是一个文件，启动的是另一个文件”。

## 三、工具定义包含什么

`ToolManagerService` 中的 `ToolDefinition` 用来描述一个工具：

| 属性 | 含义 |
|---|---|
| `id` | 程序内部使用的唯一标识，例如 `furmark` |
| `name` | 展示名称，例如 `FurMark` |
| `purpose` | 工具用途 |
| `relativePath` | 项目内的相对路径 |
| `officialUrl` | 官方下载地址 |
| `license` | 许可说明 |
| `sha256` | 文件哈希，用于完整性校验 |
| `version` | 记录工具版本 |
| `zip` | 是否为压缩包 |
| `minimumBytes` | 文件最小尺寸，用于过滤明显异常的下载结果 |

例如 FurMark 的定义包含显卡压力测试用途、官方地址、目标路径、版本和 SHA-256。

把这些内容放入统一定义中，是为了避免每个工具类自己实现一套下载和检查逻辑。后续新增工具时，只需要补充定义和特殊处理规则。

## 四、工具状态检查做了什么

状态检查的入口是：

```java
public List<ToolStatus> getStatuses()
```

它会遍历所有工具，并调用：

```java
private ToolStatus checkStatus(ToolDefinition definition)
```

一次状态检查主要包含以下步骤：

### 1. 解析配置路径

系统首先根据工具 ID 找到 `ToolPathConfig` 中对应的路径，然后转换为绝对路径。

这样接口返回结果时，既能显示项目中的相对路径，也能显示 Windows 上实际访问的绝对路径。

### 2. 检查入口文件

系统检查目标路径是否满足：

- 文件存在；
- 是普通文件；
- 文件具有可执行属性。

如果不满足，状态通常为：

```text
status = MISSING
ready = false
reason = 目标文件不存在或不可执行
```

### 3. 检查配套依赖

只检查 exe 文件还不够，因为很多工具依赖其他文件。

当前重点检查的依赖包括：

| 工具 | 配套文件 |
|---|---|
| FurMark | `gpushark.exe`、`cpuburner.exe` |
| smartmontools | `drivedb.h` |
| CrystalDiskMark | `CdmResource`、`CdmResource/DiskSpd/DiskSpd64.exe` |

如果入口 exe 存在，但依赖缺少，仍然不能标记为 `READY`。

设计原因是：工具只有在真正启动时才暴露依赖问题，会导致用户看到“准备成功”，但执行测试时才失败。提前检查可以把问题尽量暴露在准备阶段。

### 4. smartmontools 的特殊路径检查

smartmontools 的官方 Windows 包是安装器，不一定直接安装到项目的 `tool` 目录。

因此系统除了检查项目配置路径，还会检查：

```text
%ProgramFiles%\\smartmontools\\bin\\smartctl.exe
%ProgramFiles(x86)%\\smartmontools\\bin\\smartctl.exe
```

这样用户完成安装后，即使 `smartctl.exe` 位于系统安装目录，系统也可以找到它。

## 五、下载流程为什么要使用临时文件

下载时不会直接覆盖最终工具文件，而是先写入：

```text
目标文件名.download
```

zip 解压时还会使用临时目录：

```text
.目标文件名.extract
```

完整流程如下：

```text
下载到临时文件
  -> 检查 HTTP 状态
  -> 检查文件大小
  -> 检查文件格式
  -> 检查 SHA-256
  -> 解压到临时目录
  -> 检查入口文件
  -> 发布到正式目录
  -> 删除临时文件
```

这样设计的作用是：

- 下载中断时，不会把半个文件当成正式工具；
- 校验失败时，不会破坏原本可用的工具；
- 解压失败时，不会留下不完整的正式目录；
- 正式文件只在前面的检查通过后才被替换。

## 六、下载文件的校验

### 1. HTTP 状态校验

只有 HTTP 状态码为 `200` 时，系统才继续处理响应内容。

如果服务器返回 `404`、`403` 或其他状态，准备结果会记录失败原因，而不是把错误页面保存为工具文件。

### 2. 最小文件大小校验

服务器异常、网络错误或跳转页面有时会返回一个很小的 HTML 文件。

因此系统会检查下载文件大小是否达到工具定义中的 `minimumBytes`。文件过小时，会认为它可能不是有效发行包。

### 3. ZIP 文件头校验

zip 文件开头通常是：

```text
PK
```

系统在解压前先检查文件头。如果下载地址返回 HTML 页面，就不会进入解压流程。

### 4. Windows 可执行文件校验

Windows PE 文件通常以：

```text
MZ
```

开头。

对于非 zip 下载，系统会检查 `MZ` 文件头，避免把网页、JSON 或错误文本保存成 `.exe`。

### 5. SHA-256 校验

SHA-256 是根据文件内容计算出的摘要值。只要文件内容发生变化，摘要通常也会变化。

系统会把下载文件的 SHA-256 与代码中记录的官方值比较：

```java
if (!definition.sha256().isBlank()
        && !sha256(target).equalsIgnoreCase(definition.sha256())) {
    throw new IOException("SHA-256 校验失败");
}
```

校验通过说明：

- 下载内容与预期版本一致；
- 文件没有在传输过程中损坏；
- 文件不是明显的错误页面或其他内容。

对于官方没有提供固定下载文件或下载地址动态变化的工具，代码不会伪造哈希值，而是结合文件类型和最小大小进行校验，并在无法验证时返回明确原因。

## 七、ZIP 解压的安全处理

系统使用 `ZipInputStream` 读取压缩包，而不是直接调用命令行解压工具。

解压时会把每个压缩项解析成目标路径，并检查规范化后的路径是否仍在临时解压目录中：

```text
压缩包中的路径
  -> 规范化
  -> 判断是否仍位于目标目录
  -> 合法才写入
```

这是为了防止路径穿越，例如压缩包中包含：

```text
../../some-file.exe
```

如果不检查，解压可能把文件写到项目目录之外。当前实现发现非法路径后会直接抛出异常，终止解压。

解压完成后，系统还会寻找定义中要求的入口文件。只有入口文件存在，才会把临时目录中的内容发布到正式工具目录。

## 八、不同类型工具的准备方式

### 1. ZIP 工具

以下工具主要通过 zip 包准备：

- CPU-Z；
- Core Temp；
- FurMark；
- CrystalDiskMark。

处理方式是：下载 zip、校验、解压、检查入口文件和依赖、发布文件。

### 2. 动态下载工具 GPU-Z

GPU-Z 的官方下载流程需要向官方地址发送 POST 请求，不能简单地把网页地址当作普通 exe 下载地址。

系统会：

- 使用指定的 POST 参数请求下载；
- 检查 HTTP 状态码；
- 检查 `Content-Type`；
- 检查返回内容是否为 Windows 可执行文件；
- 再进行大小和 SHA-256 校验。

如果服务器返回的是下载页面 HTML，系统会拒绝保存，并返回类似“未返回可执行文件”的原因。

### 3. smartmontools 安装器

smartmontools 的官方 Windows 地址返回的是安装器，而不是可以直接放入项目目录的 `smartctl.exe`。

因此流程是：

```text
下载官方安装器
  -> 使用管理员权限启动安装器
  -> 用户在 UAC 中授权
  -> 安装器完成安装
  -> 重新扫描系统安装目录
  -> 检查 smartctl.exe 和 drivedb.h
```

这个工具不能简单地按照“下载 exe 后移动到目标目录”处理，否则会把安装器错误地当成 `smartctl.exe`。

### 4. VC++ Redistributable

VC++ x64 和 x86 的准备主要是下载官方离线安装包。真正安装时需要管理员权限。

系统支持：

```text
x64
x86
both
```

其中 `both` 表示同时准备或安装 32 位和 64 位运行库。64 位 Windows 也可能运行 32 位程序，所以实际维修时通常需要同时检查两种架构。

## 九、一键准备接口的确认机制

接口地址：

```http
POST /api/tools/manager/prepare
```

请求体：

```json
{
  "confirmed": true,
  "toolIds": []
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `confirmed` | 是否允许执行下载、写文件或启动安装器 |
| `toolIds` | 要准备的工具 ID；空数组表示全部工具 |

### `confirmed = false`

当用户还没有确认时，接口只进行状态检查，不执行下载和安装：

```json
{
  "confirmed": false,
  "completed": false
}
```

这样可以避免后端在用户不知情的情况下修改本地文件或弹出管理员授权窗口。

### `confirmed = true`

当用户明确确认后，系统才会处理缺失工具：

```json
{
  "confirmed": true,
  "toolIds": []
}
```

空数组表示全部工具。系统会先检查已存在的工具，只对状态不是 `READY` 的工具执行准备，避免重复下载。

### 未知工具 ID

如果请求中包含不存在的 ID，例如：

```json
{
  "confirmed": true,
  "toolIds": ["not-exist"]
}
```

系统会返回 `unknownIds`，并且不会执行准备操作。这样可以防止拼写错误导致用户以为某个工具已经准备成功。

## 十、一键准备为什么不能遇到失败就立即返回

一次准备可能包含多个工具。如果 FurMark 下载失败，但 CPU-Z、Core Temp 和 VC++ 都可以正常准备，系统仍然应该继续处理其他工具。

当前流程会：

```text
逐个处理工具
  -> 保存每个工具的结果
  -> 继续处理下一个工具
  -> 最后统一计算 completed
```

最终结果通过所有选中工具的 `ready` 状态计算：

```java
boolean completed = resultStatuses.stream().allMatch(ToolStatus::ready);
```

因此：

- 全部 `ready = true`，则 `completed = true`；
- 只要有一个工具失败，则 `completed = false`；
- 每个失败工具的具体原因放在自己的 `reason` 字段中。

这比“遇到第一个异常就停止”更适合工具准备场景，因为用户可以一次看到全部问题。

## 十一、这次成功响应说明了什么

本次请求：

```http
POST /api/tools/manager/prepare
```

请求参数：

```json
{
  "confirmed": true,
  "toolIds": []
}
```

返回结果中的关键字段是：

```json
{
  "confirmed": true,
  "completed": true,
  "unknownIds": []
}
```

并且 8 个工具都满足：

```json
{
  "status": "READY",
  "ready": true,
  "reason": null
}
```

这些字段分别说明：

1. `confirmed = true`：本次请求允许执行准备操作；
2. `completed = true`：所有选中的工具最终都准备完成；
3. `unknownIds = []`：没有无法识别的工具 ID；
4. `status = READY`：工具入口和必要依赖检查通过；
5. `ready = true`：后续工具调用可以使用该工具；
6. `reason = null`：当前没有错误原因。

需要注意：`READY` 表示工具已经准备好，不表示已经执行过压力测试。准备流程和实际测试流程是两个阶段：

```text
工具准备成功
  -> 调用具体检测或压力测试工具
  -> 创建任务或启动外部程序
  -> 查询进度
  -> 获取结果
```

## 十二、工具准备和工具执行的区别

### 工具准备

由 `ToolManagerService` 负责，解决的是：

- 文件是否存在；
- 文件是否可执行；
- 依赖是否完整；
- 文件是否来自预期来源；
- 是否需要安装或用户授权。

### 工具执行

由具体工具类或任务执行器负责，例如：

- `FurmarkTool` 启动 `FurMark.exe`；
- CPU-Z、GPU-Z、Core Temp 工具负责打开对应程序；
- `smartctl` 负责读取磁盘 S.M.A.R.T. 信息；
- `MemStressTaskExecutor` 启动独立 Java 子进程执行内存压力测试。

分离这两个阶段的作用是：

- 准备逻辑不会和具体业务测试逻辑混在一起；
- 工具执行前可以统一检查状态；
- 下载、安装和测试可以分别定位问题；
- 后续更换工具时，对其他业务影响较小。

## 十三、推荐的学习顺序

建议按以下顺序阅读代码：

1. 阅读 `ToolPathConfig`，理解所有工具路径从哪里来；
2. 阅读 `ToolManagerController`，理解 HTTP 请求如何进入后端；
3. 阅读 `ToolManagerService.prepare`，理解确认、筛选和结果汇总；
4. 阅读 `checkStatus`，理解 `READY` 是如何计算的；
5. 阅读 `download` 和 `downloadFile`，理解下载、校验和解压；
6. 阅读 `FurmarkTool`，理解准备好的外部工具如何真正启动；
7. 阅读 `ToolProcessRunner`，理解 Java 如何通过 `ProcessBuilder` 启动 Windows 程序；
8. 阅读 `RuntimeLibTool`，理解 VC++ 检测、确认和 UAC 安装；
9. 阅读 `MemStressTaskExecutor`，理解长时间任务、进度推送和子进程清理。

## 十四、可以继续改进的方向

当前工具准备流程已经能够完成统一检测和一键准备，但仍可以继续完善：

- 为没有固定 SHA-256 的工具增加版本清单或官方签名校验；
- 将工具定义从 Java 常量迁移到配置文件或数据库；
- 为下载增加重试和断点续传；
- 为安装器增加安装完成后的自动轮询检查；
- 增加准备流程日志，记录下载、校验、解压和安装阶段；
- 为每个工具增加独立的集成测试；
- 在前端显示每个工具的准备进度和失败原因；
- 对工具启动增加超时、退出码和进程生命周期管理。

## 十五、总结

本次完善的本质不是简单地“补几个 exe 文件”，而是建立了一套工具生命周期管理流程：

```text
工具定义
  -> 状态检测
  -> 用户确认
  -> 官方来源获取
  -> 文件完整性校验
  -> 安全解压或管理员安装
  -> 入口和依赖复查
  -> READY
  -> 进入真实检测或压力测试
```

这样设计后，CorePulse 的 AI 可以把“建议使用某个工具”和“这个工具实际上能否运行”分开处理。后端负责验证和执行，AI 负责理解用户问题、选择工具和解释结果，二者职责更加清晰。
