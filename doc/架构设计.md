> 版本: v0.2(2026-08-11,技术栈已定案)
> 状态: 已评审 —— 核心架构与技术栈确认,进入 M1 开发

---

## 1. 项目概述

### 1.1 初衷
电脑维修行业暴利、存在过度维修(如只需删软件却重装系统)。本项目面向**电脑小白**,提供一站式检测与维修引导:内存/显卡压力测试、系统重装引导、Agent 代执行(清理C盘、卸载软件等),透明、低成本、可自助。

### 1.2 目标用户
不懂硬件的普通用户。这意味着:
- 必须用"人话"沟通,AI 助手是产品的**对话本体**
- 所有破坏性操作(删文件、卸软件、重装)必须有**确认环节**
- 结果要可解释(诊断报告),不能甩一堆原始数据

## 3. 总体架构(方案 A:助手层 + Agent 执行层)

**核心原则:AI 助手是大脑(说话+决策),桌面 Agent 是工具臂(干活)。用户永远只面对助手。**

```
┌────────────────────────────────────────────┐
│ 用户(小白)                                  │
└──────────────────┬─────────────────────────┘
                   │ 聊天 / 工具卡片 / 进度
                   ▼
┌────────────────────────────────────────────┐
│ 前端(Web/桌面壳)                            │
│  · 聊天界面 · 系统信息 · 工具库 · 我的       │
└──────────────────┬─────────────────────────┘
                   │ HTTP + WebSocket(实时进度)
                   ▼
┌────────────────────────────────────────────┐
│ 后端服务(助手层 · Java/Spring Boot · 自研)  │
│  · 对话上下文管理/历史会话                   │
│  · LLM 调用(意图识别/决策/总结)             │
│  · 函数注册表(Function Calling)             │
│  · 任务管理: 创建/落库/确认/完成            │
│  · 确认环节(破坏性操作需用户确认)            │
│  · 诊断报告生成                             │
└───────┬─────────────────────────┬──────────┘
        │ 路径A:简单函数(同步)     │ 路径B:delegate_to_agent(异步)
        │                         │
        ▼                         ▼
┌──────────────┐      ┌───────────────────────┐
│ 简单工具(自研)│      │ 桌面 Agent 执行层       │
│ 硬件/磁盘/    │      │ · 复杂任务 → Hermes    │
│ 烤机/温度     │      │   (hermes chat -q)     │
│ 同步/异步执行 │      │ · 技能覆盖:磁盘清理/    │
│              │      │   硬件/网络/安全        │
└──────────────┘      └───────────────────────┘
```

### 3.1 为什么分层(为什么用户不直接面对 Agent)
- 对话、追问、解释、历史记忆是**产品本体**,省不掉,必须有人承担
- 助手层承担:理解模糊表述、多轮追问、风险确认、结果解释、历史会话
- Agent 只承担:执行,不做对话 —— 各层都简单,可独立演进
- 备选"方案B(胖Agent)"代价:对话/记忆/确认全塞进执行服务,复杂度不降反升,故弃

### 3.2 两条执行路径(决策规则)

**规则:单步秒回的走函数调用;需要多次判断、耗时长、动用户数据的走 Agent。**

| 任务 | 路径 | 原因 |
|---|---|---|
| 查硬件信息 / 磁盘空间 / 温度 | A 函数调用 | 单步、秒级返回 |
| 显卡压力测试 | A 函数调用 + MQ 延时终止 | 触发简单,监控走消息 |
| 清理 C 盘 | B Agent(Hermes) | 多步、要判断、动用户数据 |
| 卸载软件 / 清残留 | B Agent(Hermes) | 需确认、多步骤 |
| 全面体检 | B Agent(Hermes) | 多检测串联、耗时长 |

### 3.3 Agent 执行层选型结论:复用 Hermes(现成),不重复造轮子
- Hermes 具备完整技能生态:windows-disk-cleanup(清理C盘)、windows-hardware 检测、windows-network-diagnostics 等,与维修场景高度匹配
- 通过 `hermes chat -q "任务描述"` 一行命令可被外部程序(Java 后端 ProcessBuilder)调用,返回结果文本
- 自研代价高(agent loop/技能/记忆全要重写),收益低;核心价值(编排/状态机/确认环节)在后端,自研部分不受影响
- 面试叙事:"选型并集成开源 Agent 框架"是加分项,不是减分项

## 4. 核心流程设计

### 4.1 显卡压力测试(函数调用路径 · 用户原设计,不变)

1. 用户:"玩游戏蓝屏,帮我测下显卡" → 后端组装上下文调 LLM
2. LLM 决策:调用 `furmark` 工具,时长 30 分钟 → 后端匹配工具实现类、参数校验
3. 创建任务落库 → 发两条 MQ:一条立即执行、一条 30 分钟延时终止
4. Agent 探针收指令 → 本地启动 FurMark → 每秒采集温度/帧率上报(Redis + WebSocket 推前端)
5. 30 分钟延时消息到期 → 下发终止 → 探针杀进程
6. 探针解析结果标准化上报 → 后端更新 DB、清理 Redis 实时状态
7. 后端把结果拼入对话 → 再次调 LLM → 生成诊断结论返回用户

### 4.2 清理 C 盘(Agent 路径 · Hermes 执行)

```
用户: "帮我清理C盘"
助手: "收到,我先看看你C盘空间"
  → LLM 调 get_disk_space()  [路径A,秒回]
助手: "C盘剩20GB(已用50GB)。要我帮你清理吗?主要是缓存和临时文件"
用户: "清理吧"
  → LLM 调 delegate_to_agent("清理C盘", 约束="不动用户文档/软件")
  → 任务落库,后端 ProcessBuilder 调 hermes chat -q "清理C盘,不要动用户文档,输出JSON结果"
  → Hermes 执行(windows-disk-cleanup 技能),过程日志可回传
  → 如需删软件/动用户数据 → Hermes 停下,请求确认 → 助手向用户确认
  → 用户确认 → 继续 → 完成,返回结构化结果(JSON)
助手: "清理完成,释放了 8.5GB。下次可以每周自动清理一次"
```

**确认环节是硬性规则**:所有删除/卸载/重装类操作,Agent 必须停等后端转达用户确认,不得自主执行。

## 5. Agent 执行层设计(复用 Hermes)

### 5.1 对接方式(Java → Hermes)

| 场景 | 方式 | 说明 |
|---|---|---|
| 复杂任务(清理/卸载/体检) | `ProcessBuilder` 调 `hermes chat -q "任务+约束+要求输出JSON"` | 异步线程执行,stdout 解析结果 |
| 需要进度 | 任务内要求 Hermes 分阶段输出,或 Hermes 写进度文件,后端轮询 | M2 细化 |
| 需要用户确认 | prompt 中约束"遇到删除/卸载操作先停下说明",返回"待确认"状态 | 后端转前端确认 |
| 简单工具(硬件/空间/温度/烤机) | 后端自研(调用 psutil/外部工具/脚本) | 不走 Hermes,秒级 |

### 5.2 Hermes 可用技能(现成,维修场景直接复用)

- `windows-disk-cleanup`: C 盘清理
- `windows-pc-maintenance` / `windows-security-audit`: 体检类
- `windows-network-diagnostics`: 网络诊断
- `windows-process-control`: 进程/软件管理
- 自定义技能可后续补充(烤机报告、SMART 解读)

### 5.3 自研简单工具注册表(路径 A)

| 工具 | 实现 | 需确认 | 说明 |
|---|---|---|---|
| get_system_info | psutil/wmi(脚本或 JNI 封装) | 否 | 硬件信息 |
| get_disk_space | psutil | 否 | 磁盘空间 |
| get_cpu_temp / gpu_temp | LibreHardwareMonitor(管理员) | 否 | 温度 |
| smart_check | smartctl/wmi | 否 | 磁盘健康 |
| run_furmark | 进程托管 + 监控 | 否 | 烤机(异步,走 MQ) |
| run_memtest | MemTest 进程 | 否 | 内存测试(异步) |

### 5.4 Windows 实测注意点
- CPU 温度:WMI 拿不到大部分 CPU,需 **LibreHardwareMonitor**(开源,后台服务 + WMI/REST 接口),须以管理员权限运行 Agent 服务
- SMART:smartctl(Windows 版)或 WMI MSStorageDriver
- Hermes 若需管理员权限操作,以后端进程提权方式运行

## 6. 通信与中间件

| 组件 | 用途 | 说明 |
|---|---|---|
| MQ(RabbitMQ 或 RocketMQ,待选) | 任务下发、延时终止(烤机30min超时) | 用户原设计"两条消息"模式保留 |
| Redis | 任务状态、实时监控数据(温度/帧率) | 热数据,前端轮询/推送 |
| WebSocket | 前端实时进度、工具卡片 | 与 Redis 配合 |
| 数据库(MySQL/PostgreSQL) | 任务记录、历史会话、用户 | 会话持久化 |
| ProcessBuilder(subprocess) | 后端 → Hermes 调用 | 复杂任务通道 |
