> 版本: v0.3(当前)

> 历史: 早期 v0.2 曾规划引入 Hermes Agent 执行层,后经实践评估放弃(见"架构演进"),相关代码已删除。

## 1. 项目概述

### 1.1 初衷
电脑维修行业暴利、存在过度维修(如只需删软件却重装系统)。本项目面向**电脑小白**,提供一站式检测与维修引导:内存/显卡压力测试、系统文件修复、磁盘清理、系统重装引导等,透明、低成本、可自助。

### 1.2 目标用户
不懂硬件的普通用户。这意味着:
- 必须用"人话"沟通,AI 助手是产品的**对话本体**
- 所有破坏性操作(删文件、卸软件、重装)必须有**确认环节**
- 结果要可解释(诊断结论),不能甩一堆原始数据

## 3. 总体架构(纯 LLM 决策 + 工具执行层)

**核心原则:LLM 是大脑(说话+决策),后端工具是工具臂(干活)。用户永远只面对助手。**

```
┌────────────────────────────────────────────┐
│ 用户(小白)                                  │
└──────────────────┬─────────────────────────┘
                   │ 聊天 / 工具卡片 / 进度
                   ▼
┌────────────────────────────────────────────┐
│ 前端(Web/桌面壳)                            │
│  · 聊天界面 · 系统信息 · 工具库 · 我的       │
└──────────────────┬─────────────────────────┘
                   │ HTTP + WebSocket(实时进度)
                   ▼
┌────────────────────────────────────────────┐
│ 后端服务(助手层 · Java/Spring Boot)         │
│  · 对话上下文管理/历史会话                   │
│  · LLM 调用(意图识别/决策/总结)             │
│  · 函数注册表(Function Calling)             │
│  · 任务管理: 创建/落库/确认/完成            │
│  · 确认环节(破坏性操作需用户确认)            │
│  · RAG 个人知识库(检索注入上下文)           │
└───────┬─────────────────────────┬──────────┘
        │ 路径A:简单工具(同步)     │ 路径B:长任务(异步)
        │                         │
        ▼                         ▼
┌──────────────┐      ┌───────────────────────┐
│ 数据采集/检测 │      │ 压力测试 / 修复工具     │
│ 同步返回JSON  │      │ 后台进程 + MQ 调度      │
│ 硬件/磁盘/    │      │ CPU/内存/显卡压测       │
│ 温度/运行库   │      │ VC++ 运行库修复         │
└──────────────┘      └───────────────────────┘
```

### 3.1 为什么纯 LLM,不引入外部 Agent

- 对话、追问、解释、历史记忆是**产品本体**,必须由助手层承担
- 外部 Agent(Hermes)能做的复杂任务(清理C盘、卸载软件等),通过 `runShellCommand` 终端命令 + LLM 决策 + 确认环节即可覆盖,无需引入额外进程
- 减少外部依赖:少一个运行时进程,部署与维护更简单,失败点更少
- 所有操作由后端统一管控(确认/审计/安全),可控性更强
- 详见"架构演进"章节

### 3.2 执行路径(决策规则)

**规则:单步秒回的走同步工具;耗时长的压力测试走异步工具(MQ 调度)。**

| 任务 | 路径 | 说明 |
|---|---|---|
| 查硬件信息 / 磁盘空间 / 温度 | A 同步工具 | OSHI 真实采集,秒级返回 |
| 查询/检测进程、目录、网络 | A 终端命令 | runShellCommand |
| 显卡压力测试 | B 异步工具 | FurMark + MQ 延时终止 |
| CPU / 内存压力测试 | B 异步工具 | 真实进程 + MQ 调度 |
| 运行库检测 / 修复 | A / B | 扫描同步,修复需确认 |
| 磁盘清理 | A 终端命令 | runShellCommand + 确认 |

## 4. 核心流程设计

### 4.1 显卡压力测试(异步 · MQ 延时终止)

1. 用户:"玩游戏蓝屏,帮我测下显卡" → 后端组装上下文调 LLM
2. LLM 决策:调用 `startFurMark` 工具,时长默认 30 分钟
3. 后端启动真实 FurMark.exe 进程,注册到 ProcessManager
4. 创建任务落库 → 发两条 MQ:一条立即执行、一条 30 分钟延时终止
5. 进度通过 WebSocket 实时推送到前端
6. 30 分钟延时消息到期 → 延时终止 → 清理进程
7. 后端把结果拼入对话 → 再次调 LLM → 生成诊断结论返回用户

### 4.2 清理 C 盘(终端命令路径)

```
用户: "帮我清理C盘"
助手: "收到,我先看看你C盘空间"
  → LLM 调 getDiskSpace()  [同步,秒回]
助手: "C盘剩20GB(已用50GB)。要我帮你清理吗?主要是缓存和临时文件"
用户: "清理吧"
  → LLM 调 runShellCommand("del /f /q %temp%\* ...") 
  → 该命令为危险命令,后端返回"【需要用户确认】"
  → 助手向用户解释命令作用并展示原文,用户确认
  → confirmed=true 重新执行 → 清理临时文件
助手: "清理完成,释放了 8.5GB。下次可以每周自动清理一次"
```

**确认环节是硬性规则**:所有删除/卸载/重装类操作,必须停等用户确认,不得自主执行。

### 4.3 运行库修复(检测 + 修复)

1. 用户反馈"缺少 msvcp140.dll 无法打开程序"
2. LLM 调 `scanVcRedist` → 扫描已安装 VC++ 运行库与 DLL 缺失情况
3. 确认缺失 → LLM 调 `repairVcRedist` → 首次返回"需用户确认"
4. 用户确认 → UAC 提权静默安装离线安装包
5. 完成后再次 `scanVcRedist` 验证修复结果

## 5. 工具层设计

### 5.1 工具分类

| 类别 | 工具 | 实现方式 | 需确认 |
|---|---|---|---|
| 数据采集 | `getSystemInfo` | OSHI 真实采集 | 否 |
| 数据采集 | `getDiskSpace` | OSHI 真实采集 | 否 |
| 数据采集 | `scanVcRedist` | PowerShell + 注册表 | 否 |
| 终端命令 | `runShellCommand` | cmd.exe,危险命令需确认 | 视命令 |
| 压力测试 | `startFurMark` | 真实 FurMark.exe | 否 |
| 压力测试 | `startCpuStress` / `getCpuStressStatus` / `stopCpuStress` | 真实满载进程 + MQ | 否 |
| 压力测试 | `startMemStress` / `getMemStressStatus` / `stopMemStress` | 独立 Java 进程(高危) | 是 |
| 硬件检测 | `openCpuInfo`(CPU-Z) | 打开真实工具 | 否 |
| 硬件检测 | `openGpuInfo`(GPU-Z) | 打开真实工具 | 否 |
| 硬件检测 | `openCpuTemp`(Core Temp) | 打开真实工具 | 否 |
| 硬件检测 | `openAida64` | 打开真实工具 | 否 |
| 硬件检测 | `benchDisk`(CrystalDiskMark) | 打开真实工具 | 否 |
| 硬件检测 | `scanDiskDevices` / `checkDiskHealth` | S.M.A.R.T. 健康检测 | 否 |
| 修复 | `repairVcRedist` | 离线安装包静默安装 | 是 |

### 5.2 终端命令安全策略

`runShellCommand` 是 LLM 执行系统操作的通用通道,内置双重安全:

- **危险命令**(删除/格式化/关机/改注册表等):需二次确认,命令原文展示给用户,LLM 须先解释后果
- **完全禁止命令**(格式化系统盘、静默删系统目录等):即使确认也不执行

## 6. 通信与中间件

| 组件 | 用途 | 说明 |
|---|---|---|
| RabbitMQ | 任务下发、延时终止(烤机30min超时)、死信延迟队列 | "两条消息"模式 |
| Redis | 任务状态、实时监控数据 | 热数据,前端轮询/推送 |
| WebSocket | 前端实时进度、工具卡片 | 与 Redis 配合 |
| MySQL | 任务记录、历史会话、用户 | 会话持久化 |
| ProcessBuilder(subprocess) | 后端 → 真实工具调用(压测/检测/修复) | 工具执行通道 |

## 9. 架构演进记录

### v0.2 → v0.3:放弃 Hermes Agent 委派

早期(v0.2)设计引入**外部 Agent 执行层(Hermes)**,用于执行复杂任务(清理C盘、卸载软件、全面体检),通过 `delegateToAgent` 工具委派。

**实践结论**:纯 LLM + 终端命令工具 + 确认环节已能覆盖这些场景,且更简单可控。因此**放弃 Hermes**,相关代码已彻底删除:

- `AgentTool`(delegateToAgent 工具)
- `HermesTaskExecutor` / `HermesCommandRunner`(Hermes 调用封装)
- `application.yml` 中 `corepulse.agent` 配置
- 系统提示词中 Agent 委派段落

当前所有操作均由 LLM 直接调用后端工具完成,不再依赖任何外部 Agent 进程。

> 完整的历史设计(v0.2,含 Hermes 方案)见 `架构设计_历史版本_v0.2.md`。
